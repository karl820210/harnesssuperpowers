# 系統化除錯（Systematic Debugging）

遇到 bug 時，不猜、不亂改。按 4 階段系統化追蹤根因。

**核心原則：沒有找到根因之前，不准提出修復方案。修症狀就是失敗。**

## 使用時機

- Bug report
- 測試失敗
- 非預期行為
- 效能問題
- 整合問題（模組接線後行為不對）
- Build 失敗

**特別要用在這些時候**（越想跳過流程的時候越要用）：
- 時間壓力下（「趕快修」的衝動最容易導致亂猜）
- 「一個 quick fix 就好」看起來很明顯時
- 已經試了多次修復都沒用時
- 不完全理解問題時

---

## 4 階段流程

每個階段必須完成才能進入下一階段。

### Phase 1：Root Cause Investigation（根因調查）

**在嘗試任何修復之前：**

1. **仔細讀錯誤訊息**
   - 不要跳過 error/warning
   - 完整讀 stack trace
   - 記下行號、檔案路徑、error code

2. **穩定重現**
   - 能可靠觸發嗎？精確步驟是什麼？
   - 每次都發生嗎？
   - 不能重現 → 收集更多資料，不要猜

3. **檢查最近變更**
   - 什麼改動可能導致這個問題？
   - git diff、最近 commit
   - 新依賴、config 變更、環境差異

4. **多元件系統：在邊界加診斷**

   當系統有多個元件（API → Service → DB、CI → Build → Deploy）時：

   ```
   對每個元件邊界：
     - Log 進入元件的資料
     - Log 離開元件的資料
     - 驗證環境/config 是否正確傳遞
   
   跑一次收集證據 → 分析證據找出斷裂點 → 再深入調查該元件
   ```

5. **反向追蹤資料流（Root Cause Tracing）**

   當錯誤在 call stack 深處時，從症狀往上追：
   - 壞的值從哪來？
   - 誰用壞的值呼叫了這個函式？
   - 繼續往上追，直到找到源頭
   - **在源頭修，不在症狀點修**

   技巧：
   - 加 `console.error()` / `log.Error()` 在危險操作之前（不是之後）
   - 用 `new Error().stack`（或對應語言的 stack trace）顯示完整呼叫鏈
   - 在測試中用 stderr 輸出（logger 可能被抑制）

### Phase 2：Pattern Analysis（模式分析）

1. **找到可運作的範例**
   - 同 codebase 中有類似但正常運作的程式碼嗎？

2. **對照參考實作**
   - 如果在實作某個 pattern，完整讀參考實作（不要略讀）

3. **辨識差異**
   - 正常 vs 壞掉的差異在哪？
   - 列出所有差異，不管多小
   - 不要假設「這個不可能有影響」

4. **理解依賴**
   - 這個元件需要什麼其他元件？
   - 什麼設定、config、環境？
   - 它做了什麼假設？

### Phase 3：Hypothesis & Testing（假設與驗證）

1. **形成單一假設**
   - 明確陳述：「我認為根因是 X，因為 Y」
   - 寫下來
   - 要具體，不要模糊

2. **最小化測試**
   - 做最小的改動來驗證假設
   - 一次只改一個變數
   - 不要同時修多個東西

3. **驗證後再繼續**
   - 成功 → Phase 4
   - 失敗 → 形成新假設（不要在失敗的修復上疊加更多修復）

4. **不知道就說不知道**
   - 不要假裝理解
   - 研究更多或請求協助

### Phase 4：Fix（修復）— 整合 TDD 流程

1. **Red**：撰寫重現 bug 的失敗測試
2. **Green**：修復根因（不是症狀），讓測試通過
3. **Refactor**：重構，保持測試綠燈
4. **PBT**：若 bug 涉及正確性屬性（CP-xx），補 Property-Based Test
5. **迴歸**：跑完整測試套件，確認無迴歸
6. **擴散檢查**：檢查類似程式碼路徑是否有同樣問題

**單一修復原則**：
- 一次只修一個根因
- 不要「順便」改其他東西
- 不要捆綁重構

**3+ 次修復失敗 → 質疑架構**：

如果已經嘗試 3 次以上修復都失敗，這不是假設錯誤，是架構問題：
- 每次修復都在不同地方暴露新的共享狀態/耦合問題
- 修復需要「大規模重構」才能實作
- 每次修復都在別處產生新症狀

→ **停下來，與使用者討論是否需要重構架構，不要嘗試第 4 次修復。**

## Red Flags — 看到這些信號就停下來

如果你發現自己在想：
- 「先 quick fix，之後再調查」
- 「試試改 X 看看會不會好」
- 「同時改幾個地方，跑測試看看」
- 「跳過測試，我手動驗證就好」
- 「大概是 X，讓我修一下」
- 「我不完全理解但這可能有用」
- 「再試一次修復」（已經試了 2+ 次）
- 在追蹤資料流之前就提出解決方案

**以上全部代表：停下來，回到 Phase 1。**

### 使用者不滿信號

如果使用者說了以下的話，代表你的方法有問題：

| 使用者說的 | 代表什麼 |
|-----------|---------|
| 「那個不是沒發生嗎？」 | 你假設了但沒驗證 |
| 「能不能讓我們看到…」 | 你應該加診斷收集證據 |
| 「停止猜測」 | 你在沒理解的情況下提出修復 |
| 「好好想一下」 | 質疑根本問題，不只是症狀 |
| 「我們卡住了？」（語氣沮喪） | 你的方法沒用，換方向 |

**看到這些信號：停下來，回到 Phase 1。**

## Defense in Depth（修復後多層防護）

修完 bug 後，在資料流經過的每一層加驗證，讓 bug 結構性地不可能再發生：

| 層次 | 做法 | 時機 |
|------|------|------|
| Layer 1: 入口驗證 | 在 API 邊界拒絕明顯無效的輸入 | 必做 |
| Layer 2: 業務邏輯驗證 | 確保資料對此操作有意義 | 必做 |
| Layer 3: 環境防護 | 在特定環境阻止危險操作（如測試中禁止寫入非 tmp 目錄） | 視情況 |
| Layer 4: 診斷 log | 在危險操作前記錄 context | 建議 |

單一驗證點不夠 — 不同程式碼路徑可能繞過它。每一層都加。

## Condition-Based Waiting（條件式等待）

當測試用任意 sleep/timeout 導致 flaky 時：

**原則**：等待你真正關心的條件，不要猜它需要多久。

```
❌ sleep(300ms) → 檢查結果    // 猜測時間，CI 上可能失敗
✅ waitFor(條件成立) → 檢查結果  // 條件滿足才繼續
```

通用模式（語言無關）：
```
function waitFor(condition, description, timeout=5000):
  startTime = now()
  while true:
    if condition(): return
    if now() - startTime > timeout:
      throw "Timeout waiting for {description}"
    sleep(10ms)  // 輪詢間隔
```

**例外**：測試真正的時間行為（debounce、throttle）時，任意 timeout 是合理的，但必須註解說明為什麼。

## 平行派遣（多個獨立問題）

當同時面對 2+ 個**獨立**的問題（不同 test file、不同子系統、不同 bug）時，可以平行派遣多個 sub-agent 同時調查。

### 何時使用

- 3+ 個 test file 失敗，根因不同
- 多個子系統獨立壞掉
- 每個問題可以不依賴其他問題的上下文來理解
- 問題之間沒有共享狀態

### 何時不使用

- 失敗之間有關聯（修一個可能修好其他的）→ 先一起調查
- 需要理解完整系統狀態
- Sub-agent 會互相干擾（編輯同一個檔案、使用同一個資源）

### 流程

1. **辨識獨立領域** — 按壞掉的東西分組
2. **建立聚焦的 sub-agent 任務** — 每個 sub-agent 得到：
   - 明確範圍（一個 test file 或子系統）
   - 清楚目標（讓這些測試通過）
   - 限制（不要改其他程式碼）
   - 預期產出（摘要：發現了什麼、修了什麼）
3. **平行派遣** — 使用 `invokeSubAgent` 同時派遣
4. **Review 和整合** — 所有 sub-agent 回來後：
   - 讀每個摘要
   - 檢查修復之間是否衝突
   - 跑完整測試套件
   - 抽查 sub-agent 的修復品質

### Prompt 結構

好的 sub-agent prompt：
- ✅ **聚焦** — 一個明確的問題領域
- ✅ **自足** — 包含理解問題所需的所有上下文
- ✅ **明確產出** — sub-agent 應該回報什麼
- ❌ **太廣** — 「修所有測試」→ sub-agent 會迷失
- ❌ **沒上下文** — 「修 race condition」→ sub-agent 不知道在哪

## KnowHow 同步提醒

修完 bug 後，自我檢查：

> 這個 bug 的根因是「之前不知道的限制或行為」嗎？

如果是 → 按 `knowhow-sync-rules.md` 映射表同步到對應的 KnowHow 文件。

常見需要同步的情境：
- 發現了 API/框架的未文件化行為
- 座標系/渲染的隱藏限制
- 併發/鎖的非直覺行為
- 協議格式的邊界條件

## 常見合理化藉口 — 全部無效

| 藉口 | 現實 |
|------|------|
| 「問題很簡單，不需要流程」 | 簡單問題也有根因。流程對簡單 bug 很快。 |
| 「緊急，沒時間走流程」 | 系統化除錯比亂猜快。 |
| 「先試這個，再調查」 | 第一次修復定下模式。從一開始就做對。 |
| 「修好再寫測試」 | 沒測試的修復不可靠。先測試才能證明。 |
| 「同時修多個省時間」 | 無法隔離哪個有效。會引入新 bug。 |
| 「再試一次修復」（已失敗 2+ 次） | 3+ 次失敗 = 架構問題。質疑 pattern，不要再修。 |
