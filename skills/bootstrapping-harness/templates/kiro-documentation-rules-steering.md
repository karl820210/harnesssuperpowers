## KnowHow 索引

開工先掃 `docs/superpowers/knowhow-map.md` 的觸發句欄；任務命中觸發條件 → 動那個領域**之前**先讀指向的 KnowHow 段落，用到的條目在回報中引用編號。

## Commit 規則

當使用者說「commit / 提交 / 先 commit」或要求建立/修正 commit 時：

1. **先更新文件**（若本次變更涉及：比對口徑、欄位映射、去重/正規化策略、已知限制、操作方式、除錯方法）：
   - **`docs/DEV_NOTES.md`**（長期決策文件）：若涉及架構決策、取捨、新的陷阱/workaround、或放棄某個方向，更新對應段落（精煉，不是追加）
   - **`docs/CHANGELOG.md`**（變更紀錄）：在最上方新增一則，格式見下方
2. 再進行 git add/commit（commit 訊息使用中文，延續既有格式）

### `docs/CHANGELOG.md` 每則格式

- **改了什麼**（1~3 句）
- **為什麼**（症狀/根因/取捨）
- **如何驗證**（可重現步驟或觀察點；若無法驗證則寫明原因）
- **已知限制/副作用**（若有）

### `docs/DEV_NOTES.md` 更新原則

- 這是給「下一個接手的人」看的交接文件，應越寫越精煉，不是越寫越長
- 新增決策放在「架構決策與取捨」段落（ADR 風格：情境 → 決定 → 理由 → 後果）
- 放棄的方向放在「已嘗試但放棄的方向」段落
- 新的陷阱放在「已知陷阱與 Workaround」段落
- 管線有結構性變更時更新「現行管線摘要」段落

### `docs/DEV_NOTES.md` 拆分機制

當 `docs/DEV_NOTES.md` 的某個段落累積到**超過 80 行**，或某個模組/功能的內容已多到與其他段落不成比例時，agent 應主動向使用者提議拆分；經同意後將內容拆到 `docs/notes/`，並在 `.kiro/steering/` 新增對應 `fileMatch` steering 以常駐載入該模組決策。
